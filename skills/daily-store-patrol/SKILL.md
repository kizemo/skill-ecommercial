# 每日巡店

**来源**：本机 PostgreSQL 实测（`taobao` 库 + `erp` 库，7 个淘宝店铺 schema）＋ `taobao-operation` 知识库的巡店/诊断方法论｜**层级**：L1 体系层｜**版本**：2026.10

> 巡店不是"看一眼报表"，是**一条固定的诊断流水线**：每天同一时间、用同一组口径、把同一批指标过一遍，异常就自动浮出来。
> 本 skill 提供这条流水线，外加**可运行的脚本**和**异动规则库**。

## 一、快速开始

### 用脚本跑（推荐）

```bash
# 连接参数走标准 libpq 环境变量，口令走 .pgpass 或 PGPASSWORD（脚本不内置任何口令）
export PGHOST=127.0.0.1 PGPORT=5432 PGUSER=<你的用户名>

python skills/daily-store-patrol/scripts/daily_patrol.py --shop all --out patrol-today.md
```

| 参数 | 说明 |
|---|---|
| `--shop` | 店铺 schema 后缀：`haoyale`/`feite`/`fengshangzhi`/`renhe`/`zhuoguang`/`jiantai`/`darong`，或 `all` |
| `--date` | 统计日期 `YYYY-MM-DD`，默认取各表自己的最新日期 |
| `--out` | 输出 Markdown 路径，默认打印到屏幕 |
| `PATROL_DEBUG=1` | 打印完整错误堆栈 |

**脚本产出**：数据新鲜度 → 店铺大盘红绿灯 → 流量结构 → 客户资产 → 推广计划体检 → 商品巡检 → 结论与今日行动清单。

## 二、数据底座（先认清，别踩坑）

| 库 | 表 | 内容 | 实测最新 |
|---|---|---|---|
| `taobao` | `shop_<店>.core_daily_2026` | 店铺经营核心日报，**124 列**：访客/成交/转化/客单价/退款/评分/会员/四项推广花费 | 2026-10-22 |
| `taobao` | `shop_<店>.shop_traffic_source_2026` | 流量来源（**三级**）+ `归属原则`（第一次/最后一次/每一次访问） | 2026-10-22 |
| `taobao` | `shop_<店>.customer_assets_2026` | 客户资产：新客/潜客/已购/回访/复购率/粉丝分层 | 2026-10-22 |
| `taobao` | `shop_<店>.wxt_promotion_baobei_2026` / `_keyword_2026` / `_audience_2026` | 万相台三类推广：**计划/单元/人群/宝贝/词** 级，83-87 列 | 2026-10-01 |
| `erp` | `erp_result.daily_store_dd_2026` | 店铺日汇总 25 列，**含推广费用/营销费用/投产比** | 2026-10-18 |
| `erp` | `erp_result.daily_sku_dd_2026` | SKU 日汇总 38 列：销售/成本/退货/次品/换货 | 2026-10-18 |
| `erp` | `bi.dim_shop` | 店铺字典（19 店 / 平台 / 团队分组） | — |

**7 个淘宝店铺 schema**：`haoyale` 好雅乐、`feite` 飞特、`fengshangzhi` 风尚志、`renhe` 仁禾、`zhuoguang` 卓广、`jiantai` 健泰、`darong` 大融。

### 五个必须知道的坑

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | **比率字段单位混用**：同一列有时是百分数（`1.53`=1.53%），有时是小数（`0.0153`=1.53%）。实测 2026-01 是 `1.40`、2026-06-01 是 `0.0257`、2026-08-15 是 `2.01`、2026-10-22 是 `0.0153` | 转化率显示成 0.02% 或 153%，判读全错 | **按目标日期 ±3 天窗口的中位数自动判定**并归一（脚本已实现） |
| 2 | **`成功退款金额` 是"当天发生的退款"**，含历史订单退款 | 10-22 好雅乐 30130÷58930 = 51%，真实退款率是 1.29% | 退款率用 **ERP 按订单日期的 `退货金额 ÷ 销售金额`**；core_daily 的退款额只当趋势看 |
| 3 | **各源日期不同步**：店铺日报领先 ERP 约 4 天、领先万相台约 3 周 | 把不同日期的数放一张表比，结论全错 | 结论只用各源自己的最新日期；跨源对比先对齐日期 |
| 4 | **淘宝店铺在 ERP 的 `推广费用` 是 NULL** | 算不出淘宝的费比 | 淘宝推广费从 `core_daily` 的四项推广花费取（`全站推广花费`+`关键词推广花费`+`精准人群推广花费`+`智能场景花费`） |
| 5 | **ERP `类型` 含「补单」** | 销量被虚增、退款率失真 | **所有 ERP 查询必须带 `类型='真实'`** |

> 第 6 个坑（流量来源的 `归属原则` 三选一）见第 5 节。

## 三、每日巡店六步

```
第 0 步  数据新鲜度确认     ← 5 分钟，先确认数据到位
第 1 步  店铺大盘红绿灯     ← 18 个核心指标 + 5 个派生指标
第 2 步  流量结构定位       ← 问题在哪一层：流量 / 转化 / 承接
第 3 步  客户资产体检       ← 池子厚度、回访、复购、粉丝分层
第 4 步  推广计划体检       ← 三类推广逐计划判读，定重点计划
第 5 步  商品层巡检         ← 定重点商品：退货率、成本倒挂、销量骤降
第 6 步  出结论             ← 红绿灯表 + 今日行动清单 + 机会清单
```

每步的**看什么 / 怎么查 / 怎么判读 / 做什么**见 `chapters/ch02-每日巡店六步流程.md`。

## 四、红绿灯判定规则

### 相对判定（默认）

对比**自身前 7 日均值**，不用编造的绝对值：

| 方向 | 绿 | 黄 | 红 |
|---|---|---|---|
| **越大越好**（访客、支付金额、成交人数、转化率、客单价、UV价值、新客数、老客数、评分） | 跌 ≤10% | 跌 10~25% | 跌 >25% |
| **越小越好**（跳失率） | 涨 ≤10% | 涨 10~25% | 涨 >25% |
| **中性**（四项推广花费、淘客佣金、当日退款发生额） | 不打灯 | — | — |

> **为什么阈值是相对的**：不同店铺体量差几十倍，绝对值没法通用。知识库的绝对红线（体验分 4.6、PXI 70/60、大促退款率 5%、放量 ≤50%）另列在下表，**命中即处理，不看灯**。

### 绝对红线（来自知识库，命中即处理）

| 红线 | 阈值 | 出处 |
|---|---|---|
| 店铺体验分 | **< 4.6** → 失去搜索权重 + 无法报名大促 | `compliance-medical` |
| 商品体验分 PXI | **< 70** → 流量负向；**< 60** → 彻底断流 | `compliance-medical` |
| 大促退款率 | 目标 **< 5%** | `campaign-playbook` |
| 放量幅度 | 每次增幅 **≤ 50%** | `taobao-ops-playbook` |
| 间接成交 / 直接成交 | **≥ 2 倍** → 该品投放完全无效 | `store-diagnosis` |
| 领先率（新客成交占比） | ≥80% 合格｜70-80% 可接受｜50-70% 资源浪费在收割｜<50% 主要跑收割｜<30% 拉新链路已断 | `store-diagnosis` |

### 红绿灯表的用法原则（知识库：红绿灯监控法）

> **每部门不超过 3 个关键指标**；红绿灯的目的是**找问题、持续改进**，**不直接与绩效考核挂钩**。

所以巡店结论不要变成"谁扣分"，要变成"今天先动哪三件事"。

## 五、问题与机会：识别规则

### 定位问题在哪一层（流量结构）

`shop_traffic_source_2026` 的 `归属原则` 有三种，**不可混用**：

| 归属原则 | 含义 | 用来判断 |
|---|---|---|
| **第一次访问来源** | 买家第一次怎么找到你 | **拉新链路**在哪 |
| **最后一次访问来源** | 买家成交前最后那次从哪来 | **收割链路**在哪 |
| 每一次访问来源 | 全部访问 | 总量口径 |

**核心判据**（知识库归因切换法）：**最后一次访问来源的"效果广告"支付买家占比远高于第一次 ⇒ 在跑收割型定向**。

### 症状 → 原因 → 动作（速查，全表见 ch03）

| 症状 | 先查 | 大概率原因 | 动作 |
|---|---|---|---|
| 支付金额跌、访客没跌 | 转化率、跳失率 | 承接端问题（主图/详情/评价/价格） | `conversion-optimization` |
| 支付金额跌、访客也跌 | 流量结构 | 流量来源萎缩 | `wanxiangtai-wujie` / `keyword-promo` |
| 费比涨、金额没涨 | 真实投产 | 投产是假的（间接成交/收割） | `profit-model` + `store-diagnosis` |
| 新客占比 < 50% | 领先率 | 在跑收割 | `customer-asset-ops` |
| 某计划花费高、投产 < 1 | 直接成交 | 该计划无效 | `wanxiangtai-wujie` 红绿灯调预算 |
| 某计划投产高但新客数 = 0 | 成交新客数 | 只收割不拉新 | 加拉新计划 |
| 商品退货率 ≥ 20% | ERP 退货明细 | 质量/描述/尺码/预期差 | `compliance-medical` + `conversion-optimization` |
| 成本/实收 > 100% | ERP 成本 | **成本倒挂，卖一单亏一单** | 立刻停投 → `pricing-margin` |
| 沉睡粉丝多 + 复购率低 | 客户资产 | 私域没激活 | `customer-asset-ops` 召回 |

### 机会识别（别只找错，还要找增量）

| 机会信号 | 判据 | 动作 |
|---|---|---|
| 费比低于基线且投产达标 | 费比 + 真实投产 | 回收预算，加投赢家 |
| 某二级流量来源转化率显著高于店铺均值 | 流量结构 | 该来源加预算 |
| 某计划投产 ≥3 且带新客 | 推广体检 | 加预算（增幅 ≤50%） |
| 复购率与老客金额占比双升 | 客户资产 | 该品升 A 级承接 |
| 潜在客户多但成交少 | 客户资产 | 人群包 / 承接问题 |

## 六、重点关注对象：商品、推广计划、人群

### 重点商品（按 ERP SKU 日汇总，`类型='真实'`）

按优先级取：

1. **成本倒挂** —— `销售成本 ÷ 商家实收 > 100%`（🔴 立刻停投）
2. **退货率 ≥ 20%** —— `退货数量 ÷ 销售数量`（🔴 查质量/描述）
3. **销售金额环比骤降 > 50%** 且昨日有量（🔴 查断货/下架/权重）
4. **有销量无推广** —— 卖得动但没投 → 潜力品，可加投

### 重点推广计划（万相台三类，按 `计划名字` 聚合）

| 判读 | 口径 | 动作 |
|---|---|---|
| 🔴 有花费无直接成交 | `花费>0` 且 `直接成交金额=0` | 停或降预算 |
| 🔴 间接 ≥ 2 倍直接 | `间接成交金额 ÷ 直接成交金额 ≥ 2` | 投放无效，停 |
| 🔴 投产 < 1 | `总成交金额 ÷ 花费 < 1` | 停 |
| 🟡 只收割不拉新 | 投产 ≥1.5 但 `成交新客数=0` | 改定向或开拉新计划 |
| 🟡 点击率 < 1% | `点击量 ÷ 展现量 < 1%` | 换素材（`visual-material`） |
| 🟢 投产 ≥3 且带新客 | — | 加预算（增幅 ≤50%） |

### 重点人群与流量来源

- **人群**：成交新客占比高的计划 → 加投；全是老客成交的计划 → 补拉新
- **流量来源**：第一次访问来源里付费占比高、但新客数低 → 付费买到的不是新客

完整算法与 SQL 见 `chapters/ch04-重点商品与计划筛选.md`。

## Scope & Limits

- **本 skill 的数据只覆盖淘宝/天猫 7 个店铺**（`taobao` 库有 `shop_*` schema 的那些）。JD/PDD 店的数据在 `erp` 库但没有店铺侧流量/客户资产表，本流程的流量与客户资产步骤对它们**不适用**。
- **万相台数据滞后约 3 周**（实测最新 2026-10-01 vs 店铺日报 10-22）—— 推广体检结论反映的是**三周前**的投放状态，不能当"昨日"用。
- **红绿灯是相对判定**，绝对红线来自知识库；**知识库阈值是 2026 上半年口径快照**，平台规则会变，落地前核对当期公告。
- **本 skill 不给推广操作指令**，只指出该关注哪个计划；改计划走 `wanxiangtai-wujie`。
- 脚本**不内置任何数据库口令**，走标准环境变量/`.pgpass`。
