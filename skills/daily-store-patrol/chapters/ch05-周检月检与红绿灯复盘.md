# 第 5 章 · 周检、月检与红绿灯复盘

> 每日巡店解决"**止损**"；周检解决"**调结构**"；月检解决"**重新排兵布阵**"。
> 三者用同一套数据，但**看的不是同一种指标**。

---

## 一、三种节奏的分工

| 节奏 | 频率 | 核心问题 | 主要指标 | 产出 |
|---|---|---|---|---|
| **每日巡店** | 每天 | 哪里出问题了、今天先动谁 | 异动值 vs 7 日均值 | 今日行动清单（≤5 条） |
| **周检** | 每周 | 方向对不对、预算结构要不要改 | 趋势、SABC 分级、红绿灯复盘 | 下周预算表与调级方案 |
| **月检** | 每月 | 货盘要不要重排、大促准备够不够 | 货盘结构、复购、客户资产健康度 | 货盘调整方案 + 大促作战表 |

> 知识库**红绿灯监控法**的三条原则贯穿三个节奏：
> ① 每部门不超过 3 个关键指标；② 红绿灯的目的是**找问题持续改进**，**不直接与绩效考核挂钩**；③ 业务变化快的指标按周监控，变化慢的按月监控。

---

## 二、周检（每周一次，约 60 分钟）

### 2.1 周检四问

| # | 问 | 数据 | 判读 |
|---|---|---|---|
| 1 | **本周趋势对不对？** | `core_daily` 近 14 天：支付金额、访客、转化率、费比、新客占比 | 连续 7 天同向变化 = 趋势；单日跳变 = 异动 |
| 2 | **预算结构要不要改？** | `sabc-product-tiering` 的 S/A/B/C 与实际花费占比对比 | 实际与定级严重偏离 → 调级 |
| 3 | **本月促销计划达成如何？** | 周度 GSV 达成率、访客增幅、UV价值、退款率、动态体验分 | 大促复盘六指标 |
| 4 | **上周的行动清单闭环了吗？** | 上周巡店行动清单 | 未闭环的先解决，别开新战场 |

### 2.2 周检 SQL

```sql
-- 近 14 天趋势（比率字段记得单位归一）
select stat_date, "访客数","支付金额","支付转化率","客单价","UV价值","跳失率",
       ("全站推广花费"+"关键词推广花费"+"精准人群推广花费"+"智能场景花费") as 推广花费,
       "支付新买家数","支付老买家数"
from shop_haoyale.core_daily_2026
where stat_date > '2026-10-08' order by stat_date;

-- 本周计划级汇总（用万相台表自己的最新周）
select "计划名字", sum("花费"), sum("直接成交金额"), sum("间接成交金额"), sum("成交新客数")
from shop_haoyale.wxt_promotion_baobei_2026
where stat_date >= '2026-09-25'
group by 1 order by 2 desc nulls last limit 20;
```

### 2.3 周检必须产出

1. **SABC 调级表**：哪些链接升级、哪些降级、预算怎么挪（走 `sabc-product-tiering`）
2. **下周预算表**：S/A/B/C 实际占比 vs 目标占比（知识库口径：S 50%｜A 30%｜B 15%｜C 5%；**另有 S 60-70% / A 20-25% 的口径，需复核**）
3. **上周行动清单闭环表**
4. **大促期间额外**：GSV 达成率、访客增幅、转化率、UV价值、退款率（<5%）、动态体验分六指标复盘（走 `campaign-playbook`）

## 三、月检（每月一次，约 2 小时）

### 3.1 月检五问

| # | 问 | 归口 skill |
|---|---|---|
| 1 | 货盘结构健康吗？S 级占比是否达到 5%？ | `sabc-product-tiering` |
| 2 | 爆款还在正确的阶段吗？有没有该转阶段的链接？ | `hit-product-lifecycle` |
| 3 | 利润是真的吗？真实投产去伪后还剩多少？ | `profit-model` |
| 4 | 客户资产在变厚还是变薄？复购率趋势如何？ | `customer-asset-ops` |
| 5 | 下个大促准备好了吗？蓄水起跑线到了没有？ | `campaign-playbook` |

### 3.2 月检 SQL

```sql
-- 货盘结构：SKU 销售集中度
select "商品编码", sum("销售金额"), sum("销售数量"), sum("退货金额")
from erp_result.daily_sku_dd_2026
where "订单日期" between '2026-10-01' and '2026-10-18' and "类型"='真实'
group by 1 order by 2 desc limit 30;

-- 客户资产趋势（月末对比月初）
select stat_date, "用户数","潜在客户数","已购客户数","已购客户回访数","180天复购率",
       "沉睡粉丝数","活跃粉丝数","机会粉丝数"
from shop_haoyale.customer_assets_2026
where stat_date in ('2026-10-01','2026-10-15','2026-10-22')
order by stat_date;

-- 全店利润与成本（ERP 口径，看整月）
select "店铺", sum("销售金额"), sum("商家实收"), sum("销售成本"), sum("退货金额"),
       sum("推广费用"), sum("营销费用")
from erp_result.daily_store_dd_2026
where "类型"='真实' and "订单日期" between '2026-10-01' and '2026-10-18'
group by 1 order by 2 desc;
```

### 3.3 月检必须产出

1. **货盘重排方案**：新 S/A/B/C 表 + 下月预算占比
2. **爆款阶段调整表**：该转阶段的链接（打标→起量→爆发→稳定）
3. **利润体检**：各品真实投产（去伪后）+ 是否触碰斩杀线
4. **客户资产报告**：池子厚度、回访、复购、粉丝四层变化
5. **大促倒排表**（若下月有大促）：前 30 天起跑，**蓄水 KPI：O+A > 200w，O→A > 15%**

## 四、红绿灯复盘会（周 / 月）

### 4.1 会议怎么开（知识库红绿灯监控法）

| 角色 | 做什么 |
|---|---|
| 负责人 | 主持：只讨论红灯项，黄灯项是"努力方向"不是"问题" |
| 各岗 | 每个红灯项 3 分钟：现象 → 原因 → 动作 → 何时复核 |
| 老板 | **只做两件事**：定红绿灯表（明确本期重点指标）+ 跟负责人对齐具体业务动作 |

### 4.2 红绿灯表的格式

```
| 指标名称 | 目标值 | 实际值 | 完成率 | 颜色 | 改进措施 |
```

**三个坑**（知识库明列）：

| 误区 | 正确做法 |
|---|---|
| 与绩效考核直接挂钩 | 目的是找问题持续改进，不是奖惩 |
| 指标太多太杂 | 每部门 ≤3 个关键指标，抓住主要矛盾 |
| 只看数据不看过程 | 要问"为什么是红/黄"，找真正原因 |
| 一成不变不做调整 | 某指标已成常态就换新的重点 |

### 4.3 目标值怎么定（不编造）

优先级从高到低：

1. **知识库绝对红线** —— 体验分 4.6、PXI 70/60、大促退款率 5%、放量 50%、领先率四档、蓄水 200w/15%、间接成交 2 倍、SABC 预算比
2. **同行同层平均/优秀** —— AI 报告的四重对比里有这两个维度
3. **自身历史基线** —— 7 日均值（每日）、月度均值（周月）
4. **行业均值** —— 退款率超行业均值 2 倍即限流

> **原则**：目标值必须能说清出处。**说不出出处的数字不写进红绿灯表。**

## 五、三个节奏的衔接

```
每日巡店 → 产出「今日行动清单」（≤5 条，当天闭环）
    ↓ 每天的异动攒成 7 天的趋势
周检 → 看趋势 + 调预算结构 + 复盘上周行动
    ↓ 周检的结论攒成月度的结构判断
月检 → 重排货盘 + 定大促节奏 + 体检客户资产与利润
    ↓
下一轮每日巡店的基线（7 日均值）随之更新
```

**一条纪律**：**每日巡店的发现如果没有进周检，就等于没巡。** 周检是每日巡店的"消化系统"。

## 六、把节奏自动化

巡店脚本可以按 cron 每日跑，产出日报存档：

```bash
# 每天 09:10 生成前一天（或各表最新）的巡店报告
10 9 * * * cd /path/to/skill-ecommercial && \
  PGHOST=127.0.0.1 PGPORT=5432 PGUSER=<用户> \
  python skills/daily-store-patrol/scripts/daily_patrol.py --shop all --out reports/$(date +\%Y-\%m-\%d).md
```

周检/月检的 SQL 可以直接取用本仓库的章节 SQL，或让 `daily_patrol.py` 的 `--date` 参数回溯历史某天做对比。

> **建议**：巡店报告按日期存档，形成**可回溯的趋势底稿** —— 这是月检做"为什么这个月掉了"唯一可靠的数据依据。
